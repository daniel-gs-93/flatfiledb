# FlatFileDB: Testing Document

## 1. Scope and Environment

This document describes how the `flatfile` engine and the Structured Query Language (SQL) terminal around it are tested. Every test checks a claim in [DesignDocument.md](DesignDocument.md) or a decision in [DecisionRecord.md](DecisionRecord.md), cited by section or by Architecture Decision Record (ADR) number. Test IDs start with UT (unit), IT (integration), ET (environment) or MT (manual).

The matrix covers Design Document 2.1 to 2.7 and 3.1 to 3.8, and ADR-0001 to ADR-0023, except for the items below. These have no observable behavior or cannot be triggered reliably by a test.

- Diagram rendering has no automated check. MT-01 inspects the Mermaid diagrams by hand.
- Performance, including the O(n · m) matching time of `LIKE` (2.3): there is no time threshold, and the tests check only that the worst case finishes with the correct result.
- Resource ownership and container cost (2.1): code review checks them.
- Durability and process termination (2.6), failures in the rename phase of 3.3, and truncation back to the original size after a failed `AppendRows` (2.6): a test cannot induce these failures. The same applies to the kernel releasing the ADR-0015 lock after a crash, so ET-21 checks only that no lock remains after a normal exit.
- The `isatty` check and line editing of 3.6: interactive input cannot be reproduced. IT-104 checks the prompt text of `RunRepl` in `is_interactive` mode on string streams, and IT-135 the control-code text of `.clear`.
- Loading does not check `UNIQUE` or foreign keys, so a cascade over duplicate `UNIQUE` values rewrites every referencing row with that value (2.5). A test pins this known, incorrect behavior.
- An external modification that leaves both size and modification time unchanged goes undetected (2.6). The tests cover only the cases where one of them differs.
- ADR-0011 affects only cost, so IT-15, IT-54 and IT-55 check the result. The Current state entries of ADR-0004 and ADR-0006 describe `data/` and have no test.

`CMakeLists.txt` builds `flatfiledb_tests` and `flatfiledb_cli` and passes the source directory and the path of `flatfiledb_cli` to the tests as compile definitions.

The catalog fixture is the example `catalog.csv` for `data/` in Design Document 2.2: the tables `users`, `posts` and `engagements`, with `users.username` declared `UNIQUE`. Fixtures A, B, C1 and C2 all use it.

Fixture A is the main data set. Tests write the three Comma-Separated Values (CSV) files below and the catalog to a temporary directory. The headers follow `data/`, and lines end in `\n`.

| File | Content (rows after the header) |
|---|---|
| `users.csv` (`id,username,location`) | `1,alice,Paris`, `2,carol,Paris`, `3,bob,Rome`, `4,dave,Oslo` |
| `posts.csv` (`id,content,username,views`) | `10,hello world,alice,5`, `11,second post,alice,0`, `12,bobs post,bob,7` |
| `engagements.csv` (`id,postid,username,type,comment,timestamp`) | `100,10,bob,like,None,1000`, `101,10,carol,comment,nice,1001`, `102,11,bob,comment,ok,1002`, `103,12,alice,like,None,1003`, `104,12,carol,like,None,1004` |

No row references `dave`. `carol` (id 2) is referenced only by `engagements`, while `bob` (id 3) is referenced by `posts` too, so checking in row order and checking in child-table order report different first violations.

Fixture B holds rows that cannot be loaded as written.

| File | Content (rows after the header) | After loading |
|---|---|---|
| `users.csv` | `1,alice,Paris`, `x,bad,Nowhere`, `5,eve`, `1,alicia,Rome`, `2,bob,Rome` | 2 rows: `1,alicia,Rome` (the later duplicate id wins) and `2,bob,Rome` |
| `posts.csv` | `10,hello,alice,5`, `11,bad views,bob,abc` | 1 row: `10,hello,alice,5`, which loads although `alice` is not in users |
| `engagements.csv` | `100,10,bob,like,None,1`, `101,99,bob,like,None,2`, `102,10,zed,like,None,3`, `103,10,alicia,comment,hi,4` | 4 rows; loading checks no foreign keys, so `postid` 99 and `zed` are accepted |

In Fixture C1, `users.csv` holds `1,a,b` and `2,b,c`, `posts.csv` holds `10,x,a,0` and `11,y,b,0`, and `engagements.csv` has only the header. Fixture C2 differs only in `users.csv`, which holds `1,a,b` and `2,b,a`.

Fixture D covers quoting. Its catalog is one table, `notes(id INT PRIMARY KEY, body TEXT)`, and the rows of `notes.csv` are `1,"a,b"`, `2,"say ""hi"""`, `3,plain`, `4,""`, `5,"unterminated`, `6,"ok"x`.

Unit tests take their schema from `FakeCatalog`, a fake `ICatalog` with the three tables of the `data/` example and `measures(id INT, score DOUBLE)`. A decorator around `IFlatFileRepository` records the call count and arguments of each `Commit` and `AppendRows` call (the table names, in `writes`) and can make either call return a failure description.

`sample_my_db/` is a small course enrollment database: `instructors` (6 rows), `students` (30), `courses` (12) and `enrollments` (144), plus `catalog.csv`. The README examples use it, and the Environment tests that use it (ET-33 to ET-35) work on a temporary copy.

The directory permission tests make a directory unwritable, and `TempDir` restores owner permissions before it removes the directory. Permissions have no effect for the root user, so these tests end with `SKIP` there and the output marks them.

## 2. Test Strategy

### 2.1 Tiers

Unit tests use fakes, integration tests use real files in a temporary directory, and environment tests run the built executable.

| Tier | Boundary Under Test | Real Components | Replaced by Fake or Mock |
|---|---|---|---|
| Unit | Pure logic of Domain and Adapter (statement splitting, the `.schema` text); pure functions of Infrastructure (CSV and catalog encoding); Application orchestration | `SqlParser`, `Binder`, expression evaluation, `CsvCodec`, `StatementBuffer`, `FormatCreateTable`, `FormatParseError`, `QueryService` | `FakeCatalog`; `IEngine` in the `QueryService` tests |
| Integration | Across layers: `SqlParser`, `Binder`, `FlatFileEngine`, `CsvRepository`, `DirectoryLock`, `Bootstrap`, `RunRepl` (string streams stand in for stdin and stdout) and the file system | All layers under test, with the database directory in a temporary directory | `IFlatFileRepository`, through a decorator, in the write-failure tests |
| Environment | The `flatfiledb_cli` executable on copies of `data/` and `sample_my_db/`; the dependency direction of the source code | Complete system | None |

### 3.3 Environment

Environment tests run `flatfiledb_cli` against a copy of `data/`, the sample files that stay out of the repository (`/data/` is in `.gitignore`). Each test creates a working directory `work/`, copies `data/` to `work/data/`, checks that the three CSV files match the originals byte for byte, and runs `flatfiledb_cli` with `work/` as the current directory. A test that needs `data/` is skipped with `SKIP` when the directory is missing; ET-19 and ET-32 to ET-36 do not use it, and ET-16 only scans source files.

Unless a row says otherwise, the copy also gets a `catalog.csv` declaring the three tables (the `data/` example in Design 2.2), and the test sends `.open data` first. The expected result then lists only what follows, because the two lines that `.open data` prints (the `loaded` line and `users.csv: rejected lines 12, 17, 18`) are dropped before the comparison. Rows that send their own `.open`, or none, list the full output, and ET-26 compares the raw output. ET-18, ET-37 and ET-38 use a copy without the catalog. `<Tab>` stands for a tab character between columns.
