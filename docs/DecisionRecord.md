# Decision Record

This document records the design decisions of strata, a database driven from a Command-Line Interface (CLI), as Architecture Decision Records (ADR). An entry has up to five parts: the Decision, the Rationale, the Cost, the Current state (what can be observed in the system today) and the Rejected alternatives. The design is in [DesignDocument.md](DesignDocument.md) and the tests are in [TestDocument.md](TestDocument.md).

## Decisions

### ADR-0001: The engine port sits at the logical plan layer

- **Decision:** `IEngine::Execute(const PlanNode&)` takes the logical plan from the Binder. Each engine runs it with its own executor.
- **Rationale:** The project compares whole engines. With the port at the storage layer (`scan`, `lookup`, `insert`), one shared executor would sit above every engine and hide differences in operators and index choices.
- **Cost:** Each engine, flatfile included, needs its own plan executor. In return the engines can be compared on execution as well as storage.
- **Rejected:** A storage-layer port, for the reason above.

### ADR-0002: `DELETE` of a referenced row uses RESTRICT

- **Decision:** A row referenced by a foreign key of another table cannot be deleted. A `DELETE` that selects such a row returns `kConstraintViolation` and deletes nothing.
- **Rationale:** Cascading delete needs its own implementation in every engine, makes the Write-Ahead Log (WAL) record a chain of changes and multiplies the cross-engine test cases.
- **Cost:** A user has to delete the child rows first. In return every engine follows one rule.
- **Rejected:** CASCADE, for the reasons above; SET NULL, because the system has no NULL (ADR-0007).

### ADR-0003: The abstract syntax tree belongs to the Domain, and parsing stays in the Adapter

- **Decision:** The Abstract Syntax Tree (AST) types `Statement` and `Expr` live in `domain/ast.h`. `SqlParser` (Adapter) produces the AST, `Binder` (Domain) consumes it, and `QueryService::Execute` takes a `Statement`.
- **Rationale:** The Application operation is "execute one statement", so its input needs a structured form of Structured Query Language (SQL). The Binder is a pure function and can be tested in the Domain without an engine or files.
- **Cost:** The Domain holds SQL syntax structures. In return the Binder and the Application do not depend on text parsing.
- **Rejected:** Keeping the AST in the Adapter (the Application would depend on the parser); fixed query and update operations (they cannot accept every combination the syntax table allows).

### ADR-0004: flatfile loads by schema and serializes `Row` by schema on write

- **Decision:** `CsvRepository::Load` reads `catalog.csv` and parses each table's Comma-Separated Values (CSV) file into `Row` values by the `TableSchema` stored there (rules in Design Document 2.5). Two operations write: `Commit` replaces several files in one staged step (ADR-0008), and `AppendRows` appends rows. Both serialize `Row` by `TableSchema`. Rows that fail to parse are recorded by line number in `LoadedTable::rejected_lines` and reported by `.open`, because the next rewrite drops them. Loading does not check foreign keys, so those rules live only in `TableSchema::foreign_keys` (ADR-0006).
- **Rationale:** Per-column write methods cannot cover general `INSERT`, `UPDATE` and `DELETE`, and a table created with Data Definition Language (DDL) has no entity class. Dropping rows by foreign key at load time would define the rules twice and lose data silently.
- **Cost:** Orphan rows are kept and unparsable rows are not written back. In return the file equals the in-memory content, and the schema is the only source of the table definition.
- **Current state:** `data/users.csv` has 10004 lines including the header and loads 10000 rows. Line 12 `1s0,scottbates,Port Lisa`, line 17 `15,donaldfisher;Juliefort` and line 18 `15,donaldfisher,Juliefort,Aaron` cannot be loaded. `data/posts.csv` and `data/engagements.csv` have no rejected rows and no orphan foreign key. `.open` prints the number of rejected rows and the first 10 line numbers (Design Document 3.5), here `users=10000 (rejected 3)` on the `loaded` line and `users.csv: rejected lines 12, 17, 18` below it.
- **Rejected:** One write method per updatable column (each new column needs one); filtering by foreign key at load time (the rationale above); keeping unparsable rows on write-back (it needs a map from file lines to in-memory rows).

### ADR-0005: Engine capability differences are expressed as `kUnsupported`

- **Decision:** When an engine meets a plan or data it cannot execute, such as a flatfile TEXT value that contains a newline, it returns `ExecutionError{kUnsupported, <description>}` instead of terminating. The SQL front end never branches on the engine. The Binder returns its own `kUnsupported` only for features no engine supports, such as `UPDATE` of a primary key column.
- **Rationale:** flatfile is the baseline, and later engines can run more kinds of plans. The front end is shared, so capability differences surface in the response of the port.
- **Cost:** An unsupported statement is found only when it executes. In return the front end knows nothing about any engine.
- **Current state:** flatfile returns `kUnsupported` only for TEXT that contains a newline.
- **Rejected:** Checking capability in the front end (it would need to know the engine kinds); a capability query on the port (with one engine there is nothing to query).

### ADR-0006: Referential integrity rules are declared in the schema and enforced by each engine

- **Decision:** A foreign key is declared with `REFERENCES` in `CREATE TABLE` and stored in `TableSchema::foreign_keys` (column position, referenced table, referenced column position). A referenced column must be a primary key or `UNIQUE` (ADR-0013). Updating a referenced column always cascades to the referencing rows, and deleting a referenced row is always rejected (ADR-0002). Every engine enforces these rules (rule table in Design Document 2.5).
- **Rationale:** Every engine needs the same behavior, and rules kept as data can be stored by any engine that persists the catalog. A primary key cannot be updated, so a cascade happens only for a referenced `UNIQUE` column such as `users.username`.
- **Cost:** Each engine implements the checks itself, but the rules are data, not code.
- **Current state:** The 4000 distinct user names in `data/posts.csv` all exist in `data/users.csv`, and the 10000 `username` values in `data/users.csv` are distinct, so `UNIQUE` can be declared. Loading checks neither `UNIQUE` nor foreign keys. When the data contains duplicate `UNIQUE` values, a cascade rewrites every referencing row that has the same value.
- **Rejected:** Hard-coding the rules in a column handler (one handler per rule); a shared enforcement function in the Domain (it needs engine data and breaks the port boundary); an update action on foreign keys (CASCADE is the only action that can occur).

### ADR-0007: SQL semantic scope

- **Decision:** There is no NULL, and `NULL` is a reserved word that produces a syntax error. Keywords and identifiers are case-insensitive. The `WHERE` of `UPDATE` and `DELETE` accepts any `kBool` expression. An `ORDER BY` key is resolved as an integer position, an alias or a structurally identical expression, in that order, and must correspond to an item of the SELECT list. `COUNT` and `SUM` return zero on an empty set.

  `INT` is 64-bit, and `kRuntime` is returned with the message `numeric overflow` when INT overflows or a DOUBLE result is not finite. Expressions have static types, and `kBool` cannot appear in the SELECT list, in an assignment or in `DEFAULT`. A minus sign in operand position followed immediately by a numeric literal forms a negative literal, and otherwise parses as `0 - <operand>`.

  Column types accept aliases: `INTEGER` and `BIGINT` map to INT, `REAL` and `FLOAT` to DOUBLE, and `VARCHAR(n)` and `CHAR(n)` to TEXT with no length check. `NOT NULL` is accepted and has no effect. `INSERT` may omit a column that has a `DEFAULT` or is auto-increment, and `DEFAULT` is a constant expression evaluated at bind time.
- **Rationale:** Without NULL, comparison, aggregation, sorting and indexing need no three-valued logic. The header of `data/engagements.csv` is `postid` while queries write `postId`, so identifiers have to be case-insensitive, as in SQLite. Resolving `ORDER BY` against the SELECT list keeps sorting above `ProjectNode`, so a plan has one structure. Signed integer overflow is undefined behavior in C++, and a non-finite DOUBLE prints as `inf` or `nan` and compares inconsistently, so both become errors. Static types let the Binder reject `WHERE id`. Every value is already non-NULL, so accepting the `NOT NULL` of imported DDL is correct.
- **Cost:** An empty-set `SUM` returns zero where standard SQL returns NULL, `ORDER BY` cannot reference a column outside the SELECT list, `-x` overflows when `x` is the minimum `int64_t`, and the length of `VARCHAR(n)` is not checked. In return the implementation and the test scope stay smaller.
- **Rejected:** Supporting NULL (three-valued logic touches every operator); a `WHERE` that accepts only `id = <constant>` (it deviates from standard SQL); wrapping around on overflow (the result is wrong and nothing reports it); checking `VARCHAR(n)` length (the catalog would record one more length and every `INSERT` and `UPDATE` would gain a check).

### ADR-0008: A multi-file write uses a staged commit to be all-or-nothing

- **Decision:** The write set of `Commit(CommitSet)` holds `catalog.csv` when it changes, the tables whose content changed and the tables to delete. `Commit` checks the write set and writes each changed file to `<file name>.temp`. When every write has succeeded, it renames each original file to `.orig` and each `.temp` file to the original name, one file at a time (a deleted table gets only the first rename), then removes the `.orig` files. If a step fails, files that already have an `.orig` are restored from it, leftover `.temp` files and newly created files are removed, and the engine returns `kIo`. The in-memory tables are replaced only after `Commit` succeeds (flow in Design Document 3.3).
- **Rationale:** A single `UPDATE users SET username = ...` rewrites three files (users, posts and engagements), and a partial write would leave the foreign key data inconsistent at the next load. `CREATE TABLE`, `ALTER TABLE` and `DROP TABLE` change `catalog.csv` and a data file together. Written separately, they can leave a catalog entry without its file, and the database then fails to open.
- **Cost:** Each commit costs two more renames and one delete. In return every file keeps its old content when a step fails.
- **Current state:** `fsync` is not called. A process terminated during the renames leaves `.orig` behind. The load path ignores it, the next `Commit` reports a failure, and the user restores the files. If a restoring rename fails, the error names the `.orig` file that holds the original content. `AppendRows` bypasses the staged commit, so a process terminated midway leaves a half-appended row.
- **Rejected:** No rollback (the data-loss path above); a WAL in flatfile (it belongs to an engine with a different persistence format); routing `INSERT` through `Commit` (appending one row would become rewriting the whole file, which distorts the baseline's write cost).

### ADR-0009: The Binder produces plans with rule-based predicate pushdown and no cost estimation

- **Decision:** The Binder splits `WHERE` on `AND` and places each term at the lowest position where all of its columns are available (rules in Design Document 2.4). The join order follows the way `FROM` is written, chained left-deep.
- **Rationale:** With U rows in users and E rows in engagements, `WHERE u.id = 5805` without pushdown filters after the join, so the join first produces about E merged rows. With pushdown only the matching users rows enter it. Both are O(U + E); pushdown saves the merged rows and their memory.
- **Cost:** The plan shape depends on how `WHERE` is written, but no cost model or statistics are needed. Splitting on `AND` also changes short-circuit scope: a later conjunct may overflow on rows that an earlier one has already excluded.
- **Rejected:** No pushdown (temporary memory grows with E); a cost-based optimizer (it needs statistics and cost formulas).

### ADR-0010: SQL parsing uses a recursive-descent parser

- **Decision:** `SqlParser` handles SELECT, INSERT, UPDATE, DELETE, DDL and expressions with lexical analysis and a recursive-descent parser. Syntax outside the syntax table in Design Document 2.3 returns a syntax error.
- **Rationale:** The project aims to accept standard SQL, whose clauses and expressions combine freely, and the port takes a general plan, so the parse result need not map to a fixed operation.
- **Cost:** The parser is larger and needs more tests. In return new syntax is added by adding grammar rules only.
- **Rejected:** Matching fixed statement shapes with regular expressions (it cannot accept every combination, for example different `WHERE` conditions).

### ADR-0011: Equality joins use a hash join

- **Decision:** `FlatFileExecutor` splits the `ON` condition of a `JoinNode` on `AND` and takes one condition of the form "one column of left equals one column of right" as the hash join key, building the hash table from the right input and probing it with the left. The other `ON` conditions and the predicate of the `FilterNode` directly above the join are residual conditions, evaluated before a combined row is written. Without an equality condition the join is a nested loop. The plan is a left-deep chain of `JoinNode`s that each pick their own key, so the number of tables has no limit, and a key may come from any table on the left.
- **Rationale:** With 10000 rows each in users and engagements, a nested loop needs 10^8 comparisons and would overstate the join cost of the baseline, while a hash join is O(n + m). Filtering the residual conditions only after the join would let the number of temporary rows reach n · m. Running `ON u.id < p.id WHERE u.id <= 400` on a copy of `data/` on an Apple M4 produced 3,919,800 rows and used 1.46 GB (measured 2026-11-09).
- **Cost:** The executor merges the join with the filter above it. In return memory is proportional only to the number of output rows, and `ON a = b AND c` is still O(n + m).
- **Rejected:** Always a nested loop (10^8 comparisons overstate the baseline); sort-merge join (it sorts first, O(n log n)); limiting the number of tables in a join (the left-deep plan and the hash join do not depend on the count).

### ADR-0012: The flatfile CSV format and storage limits

- **Decision:** CSV columns follow Request for Comments (RFC) 4180: a value with a comma or a double quote is wrapped in double quotes, and an embedded double quote is doubled. A TEXT value cannot contain `\r` or a newline, and storing one returns `kUnsupported`. INT is 64-bit. `Commit` and `AppendRows` keep the line ending of the file's header line. The header stays as it is while the columns stay the same; `ALTER TABLE ADD COLUMN` and new files take it from the schema.
- **Rationale:** A newline is refused because the loader isolates errors line by line: a record that could span lines would let one unterminated quote swallow every row after it. The CSV files in `data/` use Carriage Return and Line Feed (CRLF, `\r\n`), and writing `\n` would mix endings.
- **Cost:** TEXT cannot hold a newline. That keeps a format error in one row from spreading.
- **Rejected:** Quoted fields that span lines (one unterminated quote would swallow the rest of the file); escaping newlines (not standard CSV, so other tools misread it); an error on any comma (users hit it with ordinary sentences).

### ADR-0013: Table definitions live in `catalog.csv` and change through DDL

- **Decision:** The schema lives in `catalog.csv` in the database directory, one row per column (format in Design Document 2.2). `CREATE TABLE`, `ALTER TABLE ADD COLUMN` and `DROP TABLE` are AST and plan nodes in the Domain, validated by the Binder and executed by the engine, which updates the catalog and the data file in one `Commit` (ADR-0008). The catalog, not the files in the directory, decides whether a table exists, and the table name `catalog` is reserved. Constraints are column-level only (`PRIMARY KEY`, `UNIQUE`, `NOT NULL`, `DEFAULT`, `REFERENCES`, `AUTOINCREMENT`), with single-column primary and foreign keys. A referenced column must be a primary key or `UNIQUE`. `ADD COLUMN` must carry `DEFAULT` and cannot carry `PRIMARY KEY`, `UNIQUE`, `REFERENCES` or `AUTOINCREMENT`. `DROP TABLE` is rejected while another table references the table.
- **Rationale:** A CSV header holds only column names, so types and keys need a home elsewhere. Without a catalog, types would be guesses (is `00123` an INT or TEXT?) and a stray file would become a table. Storing the original DDL text, as SQLite does, would put the parser in the load path and make the Infrastructure depend on the Adapter. `ADD COLUMN` takes no constraints because each would mean rechecking every old row.
- **Cost:** The catalog is one more file, table files are named `<table name>.csv` in lowercase, and there are no composite keys or table-level constraints. The schema becomes data, and both engines share one DDL front end.
- **Current state:** `data/` has no `catalog.csv`. After its CSV files are adopted with three `CREATE TABLE` statements (ADR-0014), `.open data` works.
- **Rejected:** A header with types such as `id:INT` (no longer an ordinary CSV, and keys still cannot be expressed); the schema as JavaScript Object Notation (JSON) (needs a parser or a new dependency); inferring types at `.open` (guesses); the original DDL text in the catalog (the Infrastructure would depend on the parser).

### ADR-0014: `CREATE TABLE` adopts an existing CSV

- **Decision:** When `CREATE TABLE` runs and the table's CSV already exists, the statement checks the header and parses the rows with the load rules. If the remaining rows satisfy the declared primary key, `UNIQUE` and foreign keys, the CSV stays untouched, only the catalog is written, and the rows are loaded. A violation or a header mismatch reports an error and creates no table. A 0-byte file counts as 0 rows, and the output states the number of rows adopted.
- **Rationale:** The CSV files in `data/` already exist, and attaching them beats moving them away and importing 10000 rows with `INSERT`. The declared constraints have to hold, because later RESTRICT, cascade and uniqueness checks rest on them. Unparsable rows are rejected under the load rules, so the 3 problem lines of `data/users.csv` do not block adoption.
- **Cost:** Rows rejected at adoption disappear from the file at the next rewrite, as at load (ADR-0004). Existing data needs no conversion.
- **Rejected:** Always reporting "file already exists" (the user must move the file first); overwriting the CSV (data loss); skipping validation (the declared constraints might not hold).

### ADR-0015: The database directory is protected by `flock`

- **Decision:** At `.open`, `DirectoryLock::Acquire` takes an exclusive `flock` (`LOCK_EX | LOCK_NB`) on the dedicated file `.strata.lock` in the database directory. If another process holds it, `.open` fails and the current connection stays. `OpenedDatabase` holds the lock as a `std::shared_ptr<void>`, and reopening the same directory in the same process reuses it. When the directory is not writable (creating the lock file returns `EACCES` or `EROFS`), no lock is taken.
- **Rationale:** Two processes that `.open` the same directory and then write lose data silently: the later writer rewrites the whole file from its own memory. The lock cannot sit on `catalog.csv`, because the staged commit replaces that file by rename and a lock on the old inode protects nothing. An `flock` lock belongs to each `open()`, so a process locking the same directory twice would block on itself, hence the reuse on reopen. The kernel drops the lock when the process exits or crashes, which a Process Identifier (PID) file cannot do.
- **Cost:** Only one process can open a database at a time, even one that only queries. The lock is advisory, so it cannot stop a text editor, and `flock` behaves differently on network file systems. A second writer now gets an explicit error instead of silently overwriting the first.
- **Current state:** When the lock is held, the output is `error: could not open <directory>: database is locked by another process`.
- **Rejected:** A shared lock for readers (at `.open` it is not known whether the connection will write); a PID file (left behind after a crash); a lock on `catalog.csv` (the rename defeats it); no protection (writes are lost silently).

### ADR-0016: Auto-increment takes the current maximum plus 1

- **Decision:** For a column declared `INTEGER PRIMARY KEY AUTOINCREMENT`, an `INSERT` that omits it takes the column's current maximum plus 1, or 1 for an empty table. The engine fills the value in during `PlanMutation`, because the Binder is a pure function that reads no data and only marks `InsertNode::generated_index`. An explicit value is used as given. At the `int64_t` maximum the engine reports `kRuntime` with the message `numeric overflow`. `RETURNING` is not provided.
- **Rationale:** Taking the maximum needs no extra state, so an `INSERT` stays a single-file append instead of also rewriting `catalog.csv`. A value freed by deleting the largest row is reused, which causes no dangling reference because a referenced row cannot be deleted (ADR-0002).
- **Cost:** An id can be reused after the largest row is deleted, which the `AUTOINCREMENT` of SQLite prevents, and each `INSERT` that omits the id scans the table once, O(n). There is no persistent counter to maintain.
- **Rejected:** Recording the next value in `catalog.csv` (every `INSERT` would become a two-file commit); filling the value in the Binder (it cannot read data).

### ADR-0017: The CLI ends a statement with `;`, and a statement may span lines

- **Decision:** The Command-Line Interface (CLI) accumulates input lines and ends a statement at a `;` outside a string literal. A statement may span lines, a line may hold several statements, and a lone `;` is skipped. If the input ends before the statement does, the output is `error: incomplete statement at end of input`. A command that starts with `.` is recognized only when no statement is in progress, and it takes the whole line. The exception is a line containing only `.cancel`, which discards the accumulated text when a statement is in progress outside a string literal (ADR-0023).
- **Rationale:** A longer `CREATE TABLE` needs line breaks, and `.schema` output (ADR-0018) is multi-line already. A `;` terminator is the convention of sqlite3 and psql, and without one the CLI cannot tell an unfinished statement from a one-line one. A string literal can contain `;` and newlines, so the splitting tracks whether it is inside one.
- **Cost:** A statement without a trailing `;` waits for one instead of running, which is what lets a statement span lines.
- **Rejected:** One statement per line (a long DDL cannot be broken, and `.schema` output could not be run again); a blank line as terminator (it is legal content inside a literal); a trailing `\` for continuation (not an SQL convention, and legal inside a literal).

### ADR-0018: `.schema` prints re-executable `CREATE TABLE` statements

- **Decision:** `.schema [<table>]` prints `CREATE TABLE` statements in catalog order, one column per line, each ending with `;`. The output can be fed back to the CLI and recreates the same schema in an empty database. Types are written as the standard `INT`, `DOUBLE` and `TEXT`, and `NOT NULL` is not printed. `FormatCreateTable` in the Adapter produces the text, and the Application returns only `TableSchema`.
- **Rationale:** Users want to see a table's columns and constraints and to move a schema to another directory, and printing DDL does both with no second format or parser. Referenced tables come first in the catalog, so foreign key targets exist when the output runs again. Without NULL, `NOT NULL` has no effect, so omitting it changes nothing.
- **Cost:** The Adapter holds a second textual form of DDL that has to match the parser's grammar; a round-trip test guards that. The gain is a schema that can be carried to another directory and rebuilt.
- **Rejected:** A column list in table form (it cannot be executed again); DDL text returned by the Application (the text format is presentation); the original DDL text in the catalog (see ADR-0013).

### ADR-0019: Syntax and semantics of operators, functions and `LIMIT`

- **Decision:** The binary operators `*`, `/`, `||` and `LIKE` are added. Precedence from lowest to highest is `OR`, `AND`, comparison and `LIKE`, `+ -`, `* /`, `||`, then unary minus and parentheses, and `LIKE` does not chain. `/` between two INT values truncates toward 0, and mixed operands use DOUBLE division. A divisor of 0 reports `kRuntime` `division by zero`, and dividing the minimum INT by `-1` reports `numeric overflow`. `||` accepts only TEXT. A `LIKE` pattern has `%` and `_` and no `ESCAPE`; `_` matches one 8-bit Unicode Transformation Format (UTF-8) character, and American Standard Code for Information Interchange (ASCII) letters match case-insensitively.

  The scalar functions are `LOWER`, `UPPER`, `LENGTH`, `SUBSTR`, `TRIM`, `ABS`, `ROUND` and `CAST(<expr> AS <type>)`, and the aggregates `AVG`, `MIN` and `MAX` are added. Functions and these aggregates are recognized by a name immediately followed by `(` and are not reserved words, while `LIKE`, `LIMIT` and `OFFSET` are. `AVG` returns DOUBLE, and `MIN` and `MAX` return the type of their argument. Without `GROUP BY`, `AVG`, `MIN` and `MAX` over no rows report `kRuntime` `<FN> over no rows`. `ROUND` rounds half away from zero on the binary value the DOUBLE stores, and the result is the DOUBLE nearest to the decimal value.

  A `SELECT` may end with `LIMIT <n> [OFFSET <n>]`, where `<n>` is a non-negative integer literal, and `LimitNode` sits above `SortNode`.
- **Rationale:** The precedence is SQLite's, so an expression brought over from SQLite keeps its meaning. Integer division truncates toward 0 as in C++, PostgreSQL and SQLite, and without NULL a division by 0 can only be an error. Implicit conversion would make `'id=' || 5` depend on a number format, so conversion goes through `CAST`. Without `ESCAPE` every byte of a pattern has one meaning, and the `LIKE` of SQLite is also ASCII case-insensitive. `min`, `max` and `length` are common column names, and recognizing functions by the following `(` leaves existing tables and CSV files alone. `CASE` and date functions are left for later. `ROUND` follows the stored binary value because of cases like `round(2.675, 2)`. On an Apple M4 (measured in C++ on 2026-11-11), `2.675 * 100` rounds to `267.5`, so `std::round` on the product gives `268` (`2.68`). The binary value of 2.675 is `2.67499999999999982236431605997495353221893310546875`, slightly below half, and `std::fma(2.675, 100.0, -267.5)` is `-1.7763568394002505e-14`. The rounding error of the product that `fma` recovers tells "exactly half" from "slightly below half", and sqlite3 3.51.0 returns `2.67` for the same call.
- **Cost:** `LIKE`, `LIMIT` and `OFFSET` can no longer be identifiers, and a negative `SUBSTR` start does not count from the end as it does in SQLite. The rules themselves follow from the binary value and the position, with no exceptions to remember.
- **Current state:** Tests cover the precedence of `||` and `*`, the O(n · m) matching of `LIKE`, the argument checks of functions, each runtime error message (Design Document 2.3) and the parse errors of `LIMIT`. The differential tests against sqlite3 skip the behaviors meant to differ: a negative `SUBSTR` start, `AVG`, `MIN` and `MAX` of an empty set, and division by 0.
- **Rejected:** `CASE` and date functions (new nodes in the Binder and evaluation, and no date type); implicit conversion between TEXT and numbers (the result depends on the format and conflicts with the type rules of `kBind`); `ESCAPE` for `LIKE` (a pattern byte would no longer have one fixed meaning); `LIMIT` accepting expressions (the Binder would need constant evaluation and type checking).

### ADR-0020: A multi-row `INSERT` is all-or-nothing through a single append

- **Decision:** `INSERT ... VALUES (...), (...)` produces one `InsertNode` with several `rows`. `PlanMutation` checks the rows in order and reports the first violation, and a failed statement changes nothing. A duplicate primary key or `UNIQUE` value is checked against the existing rows and the earlier rows of the same statement, a foreign key against the existing tables only. Auto-increment values increase in row order. `IFlatFileRepository::AppendRows` appends all the rows with one write and truncates the file back to its pre-append size on failure.
- **Rationale:** With `AppendRow` called once per row, a failure at row k leaves the first k - 1 rows in the file. One write also opens the file and checks its header once for N rows. Two rows of one statement can carry the same primary key, which a check against the existing rows alone cannot see.
- **Cost:** The primary key and `UNIQUE` check of `PlanInsert` builds a hash set of the existing values, O(n) for n rows, so an N-row check takes O(n + N) instead of O(n · N). A process terminated midway through the write can still leave a partial row (Design Document 2.6).
- **Current state:** For multiple rows, the Binder prefixes its error messages with `row <k>: `.
- **Rejected:** `AppendRow` row by row (not atomic); one `Commit` that rewrites the whole table (it rewrites an O(n) file only to append); `INSERT ... SELECT` (out of scope).

### ADR-0021: `.import` loads an external CSV and infers types from the data

- **Decision:** `.import <file.csv> [<table>] [--pk <column>] [--type <column>=<type>]... [--skip-bad-rows]` imports an external CSV as a new table. `Cli` parses the arguments, and `QueryService::ImportCsv` reads the source through the Domain's `ICsvSource` (implemented in the Infrastructure by `FileCsvSource`), runs the pure function `InferImport` and hands an `ImportTableNode` to the engine, which writes it in one staged commit. A column is inferred as INT or DOUBLE only when writing the parsed value back reproduces the cell exactly, and as TEXT otherwise. The default is strict, so one bad row fails the import; `--skip-bad-rows` skips and reports bad rows, and `--type` sets a type explicitly. A duplicate primary key is always an error. The rules are in Design Document 2.7.
- **Rationale:** Adopting an existing CSV means hand-writing a matching `CREATE TABLE`, the biggest barrier for a new user. A written table is rewritten in the standard format, so if inference treated `007` as INT, the next `UPDATE` would turn `007` into `7` in a column the statement never touched. The exact round-trip rule makes the import change no byte. Load rejects bad rows and reports them because the file already exists; at import the user can still fix the source, so the default is to fail. `data/users.csv` has three bad rows (the `id` on line 12 is `1s0`, and lines 17 and 18 have the wrong column count), so if every row took part in inference, `id` would become TEXT and `WHERE id = 1` would be a type error.
- **Cost:** `users.csv` cannot be imported with one command and no options, `UNIQUE` and foreign keys are not inferred (a CSV that needs them is adopted with `CREATE TABLE`), and quoted fields with newlines are not supported. The import never changes the user's data or drops it silently.
- **Current state:** `data/posts.csv` and `data/engagements.csv` each import 10000 rows with one `.import`. `data/users.csv` by default reports `line 17: expected 3 fields, found 2`, and with `--pk id --type id=INT --skip-bad-rows` it imports 10000 rows and skips 3 rows.
- **Rejected:** Inferring types by majority vote (the threshold is arbitrary, and data is dropped quietly); all columns as TEXT (what the `.import` of SQLite does, and every later numeric comparison would need a `CAST`); modifying the source file (it is the user's data); the CLI reading the file and inferring directly (the CLI only calls Application operations).

### ADR-0022: External modification is detected by file size and modification time

- **Decision:** `CsvRepository` records the size and modification time of `catalog.csv` and of each table file at load; a file that does not exist is recorded too. Before writing, `Commit` and `AppendRows` compare every file they will write or delete against the record. On a difference they return `<file name> changed on disk since it was loaded; run .open again` and write nothing. After its own successful write, the repository updates the record.
- **Rationale:** If a CSV is edited while the CLI is open, the next write statement rewrites the whole table from the old in-memory data and silently overwrites the edit. Measured on 2026-11-11: after one row was appended to `students.csv`, `UPDATE` returned the file to its original 31 lines with no message. `flock` is advisory and cannot stop an editor (ADR-0015). The check costs one `stat` per written file.
- **Cost:** An external change that keeps both size and modification time goes undetected. A rejected write means running `.open` again, which loses nothing because writes are immediate. External edits are no longer overwritten silently.
- **Current state:** After a file is modified following the load, `UPDATE`, `INSERT` or DDL returns `kIo`, the file keeps the external content, and memory is unchanged. A change in size only, or in modification time only, is detected too. The repository's own consecutive writes are not misjudged, and `.open` again recovers the state.
- **Rejected:** Merging at write time (it needs a three-way merge, and the only row identity is the primary key); content hashing (every write would read the whole file once more); a file lock (advisory); silent reload (the user's statement would run on data the user does not know about).

### ADR-0023: CLI input tolerance rules

- **Decision:** `--` to the end of the line starts a comment, and `StatementBuffer` and the lexer ignore `;` and single quotes inside it. U+00A0, U+3000 and U+2000 to U+200A count as whitespace. A full-width semicolon `；` outside string literals and comments prints `error: full-width ';' (U+FF1B) found; use ASCII ';'` and discards the line. Other unexpected characters are described by code point (`U+2019`). While a statement is in progress and the input is outside a string literal, a line containing only `.cancel` discards the accumulated text. When no statement is in progress and a line starts with a command name without the `.`, the CLI prints `error: commands start with '.'; did you mean .<name>` and discards the line. When input stops inside a string literal, the continuation prompt is `'> `. `.clear` clears the screen in interactive mode.
- **Rationale:** Scripts and pasted SQL often carry comments. A Chinese input method in full-width mode produces full-width spaces and semicolons, and curly quotes come from copied documents. These characters are invisible or look like ASCII, so the user sees only that nothing happens. The same happens after `open mydb`: the session stops at the continuation prompt and the only way out is `;` or quitting, because commands are recognized only when no statement is in progress (ADR-0017). `.cancel` is recognized only outside a string literal, because lines inside a literal are data. Ctrl-L does nothing in a terminal without line editing, hence `.clear`.
- **Cost:** `SELECT 1--2` changes meaning from "1 minus -2" to a comment, as in SQLite. A full-width semicolon makes the user retype the line, since accepting it would let input method behavior shape the grammar. A string literal left open is closed only by the closing quote or Ctrl-C. Each of these "no output" cases now gets a message or a way out.
- **Current state:** Each rule has a string-stream test. The command names recognized when the `.` is missing are `open`, `import`, `tables`, `schema`, `help`, `quit`, `exit`, `clear` and `cancel`.
- **Rejected:** Running a command name without `.` directly as a command (a mistyped `open` or similar would run as a command, MySQL style); accepting the full-width semicolon as `;` (it silently extends the grammar); `/* */` comments (they need lexer state across lines); a built-in pager and line editing (they add a dependency).

### ADR-0024: A paged database is one file in the directory, with the catalog stored in system tables

- **Decision:** `paged.db` in the database directory holds all data of the paged engine. Page 0 is the file header, and pages 1 and 2 are the first pages of the two system tables, `sys_tables` and `sys_columns`. The pages of the user tables and the system tables follow. Page numbers form one numbering space across the whole file.
- **Rationale:** The buffer pool and the planned WAL address a page by one page id and need no (file, page) pair. The catalog and the data use the same page, table heap and buffer pool mechanisms, so no second format is needed and the planned WAL protects both. Persistence has only one file to `Sync`. See Design Document 2.3 and 2.8.
- **Cost:** The pages of several tables are interleaved in the file, so the pages of one table are not contiguous in a scan. Pages are not reclaimed, so dropping a table does not return its space. In return the file has a single page id space and a single synchronization target.
- **Current state:** A new database file is 12288 bytes (three pages). The three tables in `data/` hold 30000 rows in total and occupy 548 pages: `users` 94, `posts` 295 and `engagements` 159. `paged.db` is then 2,256,896 bytes, which is 551 pages including the 3 fixed pages. Measured once on 2026-11-12 on an Apple M4 with a Release build.
- **Rejected:** One file per table plus a separate catalog file (a page id would carry a file number, the WAL would record the file number, several files would need synchronizing and the catalog would need another format); the catalog stored as a CSV or text side file (it bypasses the buffer pool and is not protected by the WAL).

### ADR-0025: A page is 4096 bytes with a common header holding a CRC-32C and an LSN, in fixed-width little-endian

- **Decision:** `kPageSize` is 4096. Every page starts with a 32-byte common header with the fields `checksum`, `page_id`, `page_type`, `slot_count`, `free_end`, `dead_bytes`, `next_page_id`, `table_id` and `lsn`. `checksum` is a Cyclic Redundancy Check (CRC) of the kind CRC-32C over the remaining bytes from offset 4, and `lsn` is the Log Sequence Number (LSN). Multi-byte integers are read and written byte by byte, little-endian and fixed-width. The CRC is sealed before a page is written out, and the CRC and `page_id` are verified after a page is read in.
- **Rationale:** (1) The page size is not larger than an operating system page and divides it evenly. The operating system page is 4096 bytes on x86 and Linux, and 16384 bytes on macOS (measured on 2026-11-11 with `sysctl hw.pagesize` on the development machine, an Apple M4). When frames and file offsets are aligned to 4096, the I/O of one page does not cross an operating system page. (2) The rows in `data/` are small. Measured on 2026-11-11 on the three CSVs in `data/`, the largest column content of a single row is 141 bytes (`posts.csv`), or about 160 bytes after encoding. A page therefore holds at least 24 rows, and the tuple cap of 4060 bytes is far larger than needed. (3) Until the planned WAL exists, the CRC is the only means to detect corrupt pages and interrupted writes (torn pages), and `page_id` detects a write to the wrong location. (4) `lsn` is reserved as 0 for now, so adding the WAL later does not change the format. (5) Byte-by-byte little-endian reads and writes make the file independent of the host byte order and of compiler alignment and padding. See Design Document 2.3.
- **Cost:** Each page gives up 12 bytes of its header to `checksum` and `lsn`, and every page read in or written out costs one CRC computation. In return corrupt pages are detected and the format does not need a revision for the WAL. The time cost of the CRC is not measured yet.
- **Current state:** The CRC-32C of `"123456789"` is `0xE3069283` (the RFC 3720 polynomial). For a page that holds data, with one bit flipped in each of the 4096 bytes, `VerifyHeader` detects all the flips as `kCorrupt`.
- **Rejected:** An 8192-byte page (the data volume is small, the frame count would halve and no measurement supports it); no checksum (until the WAL exists there is no other means to detect corrupt pages); adding `lsn` when the WAL is built (a format revision); reading and writing the header through a struct directly (the file would vary with the host byte order and the compiler alignment).

### ADR-0026: Slot numbers are stable, a RID may be reused after deletion, and an update does not cross pages

- **Decision:** A `Rid` is a page id plus a slot id. `Delete` marks the slot as dead by setting `offset` and `length` to 0, and the next `Insert` first reuses the dead slot with the lowest number. Compaction moves the live tuples to the end of the page and removes the contiguous dead slots at the tail. It does not change the number of any live slot. `Update` does not cross pages. If the new tuple fits in the same page, the original `Rid` is kept. If it does not fit, `kNoSpace` is returned and the caller runs `Delete` and then `Insert`.
- **Rationale:** Stable slot numbers make compaction move only bytes, so a holder of a `Rid`, such as the planned index, does not need to update anything on compaction. Reusing dead slots keeps the slot array from only growing. Moving a tuple across pages changes its `Rid`. That decision belongs to the execution layer and the index together, so the paged layer does not make it in advance. See Design Document 2.5.
- **Cost:** A `Rid` may point to different rows before and after a deletion, so a holder must remove its entry when the row is deleted. A longer new tuple that does not fit in the same page gets a new `Rid`. In return compaction and in-place updates do not affect the `Rid`.
- **Current state:** After a deletion, the next insert in the same page returns the lowest previously dead slot number. 20000 random operations (insert, delete, update, get, scan) agree with a `std::map<Rid, Row>` reference, for each of the two replacement policies, with three seeds.
- **Rejected:** No slot reuse (the slot array only grows and each dead slot occupies 4 bytes forever); a forwarding pointer for cross-page updates (a read needs an extra hop, the format is more complex and the execution layer has no need for it); renumbering slots on compaction (every `Rid` holder would need an update).

### ADR-0027: A tuple is encoded in schema column order, capped at 4060 bytes, with no overflow

- **Decision:** `TupleCodec` encodes a row column by column in the order of `TableSchema::columns`. INT takes 8 bytes little-endian, DOUBLE takes the 8-byte IEEE 754 bit pattern, and TEXT takes a 2-byte length plus the content. A tuple stores no column count, type or NULL bitmap. A tuple is at most 4060 bytes, and a page then holds only that one tuple. A larger tuple returns `kTooLarge`.
- **Rationale:** The system has no NULL, so a tuple needs no NULL bitmap. The schema comes from the catalog, so a tuple does not repeat the column types, and the bytes saved per row let a page hold more rows. Encoding in column order makes decoding a single pass. The largest row in the existing data is about 160 bytes (ADR-0025), and an overflow page would need a new page type, links and deletion rules, with no demand for it. See Design Document 2.4.
- **Cost:** Old tuples cannot be decoded after a schema change, so `ALTER TABLE ADD COLUMN` needs a table rewrite or a version marker, which is not decided yet. A value larger than one page cannot be stored. In return a tuple carries no extra metadata per row.
- **Current state:** `DOUBLE` is copied bitwise, and the bits of `-0.0` and `NaN` round-trip unchanged. A tuple of 4060 bytes in total succeeds, and one of 4061 bytes returns `kTooLarge`.
- **Rejected:** A type tag per column (one extra byte per row times the column count); a column offset array (it serves the read of a single column only, while all current access decodes the whole row); an overflow page (no demand).

### ADR-0028: The buffer pool synchronizes with one pool mutex and one latch per frame

- **Decision:** `BufferManager` protects the page table, the frame metadata, the free list, the replacement policy and the counters with one `std::mutex`, called the pool mutex. Each frame has one `std::shared_mutex` that protects the page content. A pin and a latch are held only by the RAII `PageGuard`, whose destructor releases the latch first and then the pin. The pool mutex is not held while waiting for a latch. On a miss, writing back the dirty victim page and reading in the new page run inside the pool mutex. When no frame can be replaced, `kNoFrame` is returned and the call does not wait.
- **Rationale:** This design prevents a data race on the page table and the metadata, a lost update of the dirty flag and the pin, and a deadlock. The lock order is latch first and pool mutex second, and a holder of the pool mutex waits for no latch, because the replaced frame has no pin. Doing the I/O inside the mutex gives "write back the victim page" and "another thread reads in the same page" a definite order, so no per-frame I/O state or set of write-backs in progress is needed. The RAII guard releases the pin on every path, including early returns and errors. See Design Document 2.6.
- **Cost:** Misses are serialized. During a disk I/O every other `FetchPage` waits for the pool mutex, a hit included. In return the implementation needs no frame state machine and the lock order can be reasoned about. The cost of serializing misses is not measured yet. It is to be measured before deciding whether to move the I/O out of the mutex.
- **Current state:** `hits + misses` equals the number of `FetchPage` calls, failed calls included. After each of the error paths (read, write back, allocation, sync and corrupt page), `PinnedFrameCount()` is 0. ThreadSanitizer reports nothing when 8 threads scan data larger than the pool at the same time, and when one writer and 4 readers access the same table at the same time.
- **Rejected:** Moving the I/O out of the pool mutex and coordinating with a frame load state plus a condition variable (the correctness cost is high and no measurement shows a need); locking per page table bucket (the concurrency scope is many readers and a single writer, with no demand); waiting for a latch inside the pool mutex (it deadlocks with a thread that holds a latch and then needs the pool mutex).

### ADR-0029: The replacement policy is an interface, implemented as LRU and simplified 2Q

- **Decision:** `IReplacementPolicy` is a state machine without locks, with the operations `RecordLoad`, `RecordAccess`, `SetEvictable`, `Evict` and `Remove`. `BufferManager` calls it inside the pool mutex. Two policies are implemented: `LruPolicy`, for Least Recently Used (LRU), and a simplified `TwoQPolicy`. In `TwoQPolicy` the A1in target is 1/4 of the capacity, A1out keeps 1/2 of the capacity in page ids, and a frame in A1in does not move when it is accessed again. `BufferManager` selects the policy through `ReplacementPolicyKind`, and the default is `kLru`.
- **Rationale:** The project compares the hits and misses of the two policies on the same access sequence, so both are implemented and can be switched. 2Q lets the pages loaded by a one-off sequential scan enter only A1in, so they do not push out the repeatedly used pages in Am. LRU has no such protection. The policy contains no lock and no I/O, so fixed operation sequences are enough to verify it. See Design Document 2.7.
- **Cost:** `TwoQPolicy::Evict` takes O(N) at worst when many frames are pinned, where N is the number of frames, and the simplified version has no adaptive A1in size. In return two policies can be compared side by side and the implementation stays simple.
- **Current state:** Given the same access sequence under both policies (capacity 8, a hot set of 4 pages, 8 filler pages and 40 one-off scan pages), the last round over the hot set has 4 misses with LRU and 0 with 2Q. The same file opened with 16 frames under each policy, repeating the sequence "scan H, F, G, H, B, H" (page counts 4, 12, 4, 60), has 4 misses with LRU and 0 with 2Q in the last scan of H (measured once on 2026-11-12). The rows of each scan are the same under both policies.
- **Rejected:** LRU only (there is nothing to compare against); Clock, LRU-K and ARC (outside the current scope; no other rejection reason is recorded).

### ADR-0030: Disk I/O is isolated behind `IPageStore`

- **Decision:** `IPageStore` is an interface owned by the paged layer. Its operations are `ReadPage`, `WritePage`, `AllocatePage`, `PageCount` and `Sync`, and all of them work in units of whole pages. `FilePageStore` implements it with the POSIX calls `pread`, `pwrite` and `fsync`, and `Sync` uses `F_FULLFSYNC` on Apple platforms. `MemoryPageStore` implements it with an in-memory page array that can inject read, write, allocation and sync failures.
- **Rationale:** Read, write, allocation and sync failures cannot be reproduced reliably on a real file. The error paths of `BufferManager`, `TableHeap` and `Catalog` (no leaked pin, no lost dirty page, undo of table creation) need failures injected deterministically. Unit tests need no file. A second implementation, `MemoryPageStore`, already exists, so the interface has a reason to exist. See Design Document 2.2 and 2.9.
- **Cost:** The paged layer carries one more interface and one implementation that only tests use. In return the error paths are verified deterministically.
- **Current state:** `Sync` of `FilePageStore` calls `fcntl(F_FULLFSYNC)` first on Apple platforms and falls back to `fsync` on failure. `MemoryPageStore` can fail the n-th read, write, allocation or sync counted from now, which is how error propagation and the absence of leaked pins are verified. Whether `F_FULLFSYNC` and `fsync` flush the data out of the storage device cache cannot be observed inside the process, and there is no test.
- **Rejected:** Calling POSIX functions directly (failures cannot be injected); a mock framework (the project has no external test framework).

### ADR-0031: The free-space map of a table heap exists only in memory

- **Decision:** Opening a `TableHeap` walks the whole page chain, reads the header of each page and rebuilds the chain tail and the in-memory free-space map. The map is a `std::set` ordered by capacity plus a `std::unordered_map` from page id to capacity. The free-space map is not written to the file.
- **Rationale:** A persisted free-space map would be another kind of page, and its updates must stay consistent with the updates of the data pages. There is no cross-page atomicity until the planned WAL exists. The data in `data/` is about 30,000 rows, estimated at about 600 pages from the average row length, so the rebuild reads only about 600 headers. See Design Document 2.5.
- **Cost:** Opening each table costs O(P) page reads, where P is the number of pages. In return the format stays simple and there is no second copy of data to keep consistent.
- **Current state:** Opening twice gives the same free-space map, and the map equals the one maintained step by step over 500 random inserts and deletes. The three tables in `data/` have 548 pages in total, where the estimate was about 600. Opening the three tables, which rebuilds the free-space map, takes about 4.2 milliseconds in total. Measured once on 2026-11-12 on an Apple M4 with a Release build and 64 frames, not repeated.
- **Rejected:** A persisted free-space map page (updates must be consistent with the data pages, and there is no atomicity until the WAL exists); a directory page recording the remaining space of each page (same reason); walking the whole chain on every `Insert` to find space, which costs O(P).

### ADR-0032: The catalog is cached on read, and table creation has no transaction protection

- **Decision:** `Catalog::Load` walks the two system tables, validates them and builds an in-memory cache. The cache is a vector of schemas plus a `std::unordered_map` keyed by lowercase name. `FindTable` and `TableNames` read only the cache, and a `std::shared_mutex` protects it. `CreateTable` runs these steps in order: it allocates the first page of the table, inserts one row into `sys_tables` and the column rows into `sys_columns`, and updates `next_table_id` in the file header. When a step fails, the system table rows already inserted are deleted on a best-effort basis, and when the undo also fails, the error message reports both failures. The cache is updated only on success. `Load` also verifies that `next_table_id` in the file header is greater than every `table_id`, so a leftover of "row inserted but `next_table_id` not yet updated" is detected, and the number is not reused at the next table creation. The name of a user table cannot start with `sys_`.
- **Rationale:** The Binder calls `FindTable` for every statement. Scanning the system tables each time costs O(T × C) decodes, where T is the number of tables and C is the number of columns per table, and the cache makes it O(1) plus one copy. The system tables use `TableHeap`, so the planned WAL protects them together with the data. Until then there is no transaction, and best-effort undo plus the validation in `Load` is the largest protection available. See Design Document 2.8 and 3.4.
- **Cost:** Table creation that terminates midway leaves pages and rows behind. `Load` detects them and returns `kCorrupt`, and there is no repair. In return the paged layer needs no transaction mechanism for now.
- **Current state:** After a failed `CreateTable`, with a failure injected at the second allocation, reopening the database succeeds and no system table row is left. After the injection is cancelled, the same `CreateTable` succeeds. `Load` returns `kCorrupt` for each of 12 kinds of inconsistent system tables and file headers, and the message names the table or column.
- **Rejected:** Serializing the whole catalog into one page blob (the number of tables and columns would be limited by a single page); scanning the system tables on every `FindTable`; no undo when `CreateTable` fails (a single I/O failure would make the database impossible to open).

### ADR-0033: The engine is named `paged`

- **Decision:** The second storage engine is called `paged`. The name is used in the directories `include/strata/paged/` and `src/paged/`, in the namespace `strata::paged`, in the argument of `.engine flatfile|paged` and in the documents.
- **Rationale:** The name describes the mechanism, storage in units of pages, and is symmetric with `flatfile`, so the difference between the two engines shows in the names. The name appears in every file path and namespace, and deferring the decision would make a later rename cover all of the paged code.
- **Cost:** The name `paged` does not point to a specific implementation. The engine is still called `paged` if the page organization is replaced later. In return the names of the two engines each describe their storage mechanism.
- **Current state:** The directories `include/strata/paged/` and `src/paged/` and the namespace `strata::paged` exist. The engine name is reviewed together with the project name, and the final name is not decided yet. The type names inside `paged` carry no engine name (ADR-0035), so a rename affects the namespace, the directories, the argument of `.engine`, the `test_paged_` prefix of test function names and the prefixes of test IDs (`PU-`, `PI-`, `PE-`).
- **Rejected:** A product-style code name (the name does not show the storage mechanism); `page` (too short and confusable with a common noun).

### ADR-0034: Each frame latch occupies one cache line

- **Decision:** Each frame latch (`std::shared_mutex`) of `BufferManager` is aligned with `alignas(kCacheLineSize)`, and `kCacheLineSize` is 128. The latch array is allocated with the C++17 over-aligned `operator new`. The latch addresses of adjacent frames differ by at least 128 bytes. The frame metadata (`page_id`, `pin_count`, `is_dirty`) is not aligned, is packed tightly and is protected by the pool mutex.
- **Rationale:** Readers update the internal state of a latch with atomic operations outside the pool mutex. When the latches of adjacent frames share one cache line, threads that take the latches of different frames invalidate each other's cache lines. This is false sharing. It reduces the scalability of concurrent reads, and it is not visible in the code but appears only in measurement. The cache line of the development machine, an Apple M4, is 128 bytes (measured on 2026-11-11 with `sysctl hw.cachelinesize`), not the 64 common on x86. The value 128 covers both. The metadata is serialized by the same pool mutex and only one thread updates it at a time, so alignment has no benefit. Packing it tightly gives the accesses to the replacement policy and the counters better locality. See Design Document 2.6.
- **Cost:** Each frame latch is padded to a multiple of 128 bytes. `std::shared_mutex` is 168 bytes on the development machine (measured with `sizeof` on 2026-11-15, Apple clang with libc++), so an aligned latch takes 256 bytes, which is 88 more than without alignment, and the array for 256 frames is 64 KiB. In return there is no false sharing between the latches of different frames. The actual effect on scalability is not measured yet.
- **Current state:** `FrameLatchAddress` shows that the latch address of each frame is a multiple of 128, that adjacent addresses differ by at least 128, and that the start of the frame memory is a multiple of 4096. Comparing with and without alignment needs an unaligned version, and the method for building one is not decided yet. The alignment is a compile-time constant, so removing it means changing the build.
- **Rejected:** No alignment (whether false sharing is visible under reads from 8 threads is not measured yet, but there is no reason to accept it in advance); putting the metadata and the latch in one aligned struct (the metadata is already serialized by the pool mutex, and alignment would only waste memory); sizing with `std::hardware_destructive_interference_size` (the standard library of Apple clang has no reliable implementation).

### ADR-0035: Type names in the paged layer carry no engine prefix, and a table's page chain is called `TableHeap`

- **Decision:** The types inside `strata::paged` do not take the `Paged` prefix. They are `Database`, `Catalog`, `DatabaseOptions` and `PageResult<T>`, and the files are `paged/database.h` and `paged/catalog.h`. The page chain of a table is called `TableHeap`, in the file `paged/table_heap.h`, and the documents call it the table heap. Test function names keep the `test_paged_` prefix.
- **Rationale:** The types are already inside the `paged` namespace, and `paged::PagedDatabase` repeats the engine name. The engine name is reviewed together with the project name, and type names without it keep a rename from touching these types. `IPageStore`, `BufferManager`, `PageGuard` and `PageError` in the same namespace have no prefix, so the prefix would appear on only 4 types. `PageResult` and `PageError` share the same stem. For the page chain of a table, the "File" in `HeapFile` refers to a series of pages, while the real files in this project are `paged.db` and the CSVs of the flatfile engine. The object returned by `Database::Table(name)` is named after its internal arrangement, not after its role. `TableHeap` keeps the "heap" used by textbooks and PostgreSQL and drops "File". See Design Document 2.1, 2.2 and 2.5.
- **Cost:** Code outside `paged` has to write `paged::Database` and `paged::Catalog` to tell which engine is meant. In return the type names are independent of the engine name. `PageResult<T>` is also used for the return values of operations that are not page operations, for example table creation, and its semantics are narrower than those of `Result<T>`. In return its stem is consistent with `PageError`.
- **Current state:** The code and the documents use these names: `paged::Database`, `Catalog`, `DatabaseOptions`, `PageResult<T>` and `TableHeap`.
- **Rejected:** Keeping `HeapFile` ("File" is confused with the real files); `PageChain` (the name is tied to the current chained arrangement and would stop fitting if directory pages replace it later); keeping the `Paged` prefix (it repeats the namespace, and an engine rename would also rename 4 types).

### ADR-0036: Operators are pull-based row iterators, and `LIMIT` terminates early

- **Decision:** Each paged plan node corresponds to one `IOperator`, and `Next()` returns one row at a time. Scan, Filter, Project, the left side of a join and Limit stream their rows. Sort, Aggregate and the right side of a join are blocking: they read their whole input at the first `Next`. `LimitOperator` stops asking the child operator for rows after it has returned `limit` rows, and with a `limit` of 0 it requests no row. An operator has no open and close step. Building the operator tree reads no data row. The first use of a table opens its `TableHeap`, which walks the page chain once. See Design Document 2.2 and 2.3.
- **Rationale:** (1) With one row at a time, the output of a join needs no buffering, and memory is proportional only to the input of the blocking operators. flatfile solves the same problem by merging the join with the filter above it (ADR-0011). (2) `SELECT ... LIMIT k` reads only the pages needed to produce k rows. That is a measurable difference between paged and flatfile, and the benchmark workloads can show it. Opening a `TableHeap` at the first use of each table walks the whole page chain, which is O(P). This cost is paid once, and `RowCounts()` of `.open` has already paid it. (3) The iterator interface is the Volcano model of Graefe (Design Document 6). Open is merged into the first `Next`, because `HeapScan` holds no page pin between two `Next` calls and an operator has no resource that needs release at close.
- **Cost:** Each operator adds one virtual call and one `std::variant` return value per row, and the rows below `LIMIT` that are never read are never evaluated. flatfile computes the whole child plan first, so a division by 0 in row 100 is reported by flatfile and not by paged (Design Document 2.6). In return memory is proportional only to the input of the blocking operators, and `LIMIT` terminates early.
- **Current state:** The operators of Design Document 2.3 exist in `paged/operators.cpp`: `ScanOperator`, `FilterOperator`, `ProjectOperator`, `HashJoinOperator`, `NestedLoopJoinOperator`, `AggregateOperator`, `SortOperator` and `LimitOperator`. Building a tree reads no data row, and a finished operator never asks its child again (XU-13). `LIMIT 0` asks its child for nothing, also with an offset (XU-12). Every error below it is dropped, including the errors below a `Sort` or an `Aggregate`, while flatfile reports them (XI-19, ADR-0044). A positive `LIMIT` above a `Sort` makes the `Sort` read its whole input. XE-03 printed a first timing. It comes from one run of the test in a Release build on an Apple M4, with the median of 3 runs for the import and of 5 runs for each query workload. It is a first measurement, not a conclusion. `LIMIT 10` without `ORDER BY`: flatfile 0.529 ms, paged 0.008 ms. The four README queries: flatfile 2.37 ms, paged 9.04 ms. Three-table join with `GROUP BY`: flatfile 6.16 ms, paged 12.46 ms. Import of the three CSV files: flatfile 26.9 ms, paged 30.2 ms.
- **Rejected:** Vectorized execution that processes a batch of rows at a time (a batch boundary would need to be defined for every operator, and no measurement so far shows a need for it); every operator fully materializing its output (the number of rows after a join can reach n · m, as ADR-0011 notes); a push-based dataflow (early termination of `LIMIT` would need another cancellation mechanism).

### ADR-0037: Operators and constraint checks are pure logic that read through `IRowStream` and `ITableReader`

- **Decision:** `paged/operators`, `paged/mutation_planner` and `paged/row_keys` read data only through `IRowStream`, `ITableReader` and `domain::ICatalog`. The paged layer owns the first two interfaces. These files do not include `BufferManager`, `TableHeap`, `Database` or `Catalog`. `paged/heap_access` implements `IRowStream` and `ITableReader` and applies a `MutationPlan` to `TableHeap`. `tests/test_layering.cpp` checks this separation. See Design Document 2.1.
- **Rationale:** Pure logic stays separate from resource handling. Constraint checking is the part of the execution layer most prone to error, and the corresponding flatfile implementation is about 500 lines. It needs many test cases, and with the storage layer replaced by an in-memory `std::vector` the cases need no page, buffer pool or file. When the planned indexes arrive, an index lookup can become another entry point of `ITableReader`, and the rules of the planner and the operators do not change.
- **Cost:** The design adds one interface layer and one more move of a row, because `HeapScan` has already decoded the row into a `Row` and `StoredRow` wraps it once more. `StoredRow` and `ScanItem` have the same content and are defined separately, so the row layer does not include `table_heap.h`. In return the pure logic can be tested independently.
- **Current state:** The row layer (`row_stream.h`, `row_keys.h`, `operators.h`, `mutation_planner.h` and their sources) includes only `domain/`, `paged_types.h`, `tuple_codec.h` and its own files. `heap_access.h` implements `IRowStream` as `HeapRowStream` and `ITableReader` as `DatabaseTableReader` over `TableHeap` and `Database`. `StoredRow` and `ScanItem` are two types with the same content. XU-32 checks the include rules, among them that `bootstrap.cpp` is the only file outside `paged/` that includes a `paged/` header. The operators (XU-01 to XU-15) and the mutation planner (XU-16 to XU-27) run over in-memory `std::vector` streams, with no page, pool or file.
- **Rejected:** Operators using `TableHeap` directly (every test case would need to create pages and a pool); putting the interface in the Domain (only paged uses it and `Rid` is a paged concept, and ADR-0030 likewise lets the layer that uses an interface own it).

### ADR-0038: A write statement computes a change set before applying it, and a failed apply is undone from before-images

- **Decision:** `INSERT`, `UPDATE` and `DELETE` run in two phases. `PlanMutation` only reads. It checks all constraints and returns a `MutationPlan`, in which each `TableChange` holds the added rows and the updates and deletes, each with its before-image. Only `ApplyChangeSet` modifies `TableHeap`. It records an undo record immediately after each successful action, and an update that moves a row records the `Delete` and the `Insert` separately. On a failure it undoes the records in reverse order, and when an undo `Update` returns `kNoSpace` it uses `Delete` plus `Insert` instead. When the undo fails, the error message gets `; rollback failed: <message>` appended. See Design Document 2.4.
- **Rationale:** (1) One `UPDATE users SET username` rewrites the three tables users, posts and engagements, so a constraint violation has to be detected before any page is modified. ADR-0008 describes the same scenario. (2) An I/O failure midway through the apply, such as writing back a dirty victim page when the buffer pool replaces a page, has no WAL to handle it until the planned WAL exists. With undo, one I/O failure leaves a table inconsistent only when the undo also fails. Without undo the inconsistency is certain. (3) Computing the change set first lets tests of pure functions prove that a rejected statement changes no table, with no need to inspect pages.
- **Cost:** Every write statement keeps the selected rows and their before-images in memory, in a size proportional to the number of selected rows. Undo restores the content and the number of rows. It does not guarantee the `Rid` or the position of a row inside a page. When the undo fails, the table may contain partial changes. Until the planned WAL exists, nothing is guaranteed when the process terminates midway. In return pages are never touched on a constraint violation, and an I/O failure can be undone.
- **Current state:** `PlanMutation` returns a `MutationPlan` and touches no page. `ApplyChangeSet` applies it, records an undo entry after each successful action and undoes in reverse order on a failure. XU-16 to XU-27 test the planner. XI-04 shows that a rejected statement leaves the bytes of every page and `page_writes` unchanged, whether the cause is a constraint violation, an evaluation error or an overlong row. XI-05 fails the n-th `WritePage` for every n of an `UPDATE` with a cascade, a 300-row `INSERT` and a 150-row `DELETE`. The tables return to the state before the statement unless the failure came from the write-back. Three hand-made change sets cover the undo order, an undo `Update` that falls back to `Delete` plus `Insert`, and an update that moved a row. XI-06 fails a read inside the undo and gets `; rollback failed: <message>`.
- **Rejected:** Modifying while scanning (on a constraint violation part of the pages would already be changed, and the scan would also see its own modifications); no undo (one I/O failure would leave half a cascade and break the foreign key); writing the undo records into a file (that is a WAL, and the WAL is planned for later).

### ADR-0039: The paged constraint rules are implemented independently and cross-checked by the cross-engine equivalence tests

- **Decision:** `paged/mutation_planner` and `paged/operators` do not use the `FlatFileExecutor` of flatfile, and the shared rules are not moved into the Domain. The rules are specified in DesignDocument 2.3 and 2.5, and the error messages are identical word for word. The equivalence tests of Design Document 2.6 cross-check the two implementations.
- **Rationale:** (1) ADR-0001 decided that the two engines do not share an executor, because the project compares whole engines. (2) `FlatFileExecutor` is in the Infrastructure on the flatfile side, and `paged/` cannot include it without breaking the dependency direction. (3) Moving the shared rules into the Domain needs a change to `flat_file_executor.cpp` (1335 lines), which is already verified. flatfile is the baseline that paged is compared with, so it is not changed before the benchmarks are run, apart from the one change under Current state. (4) Two independent implementations make the equivalence tests meaningful, because an error in one does not automatically appear in the other.
- **Cost:** The constraint rules and error messages exist in two copies, about 500 lines of duplicated rules. When a rule changes, both places have to change, and the equivalence tests are the only synchronization mechanism. In return the baseline stays as it was, apart from the one change under Current state, and the two implementations check each other.
- **Current state:** `paged/mutation_planner.cpp` and `paged/operators.cpp` are separate from `flat_file_executor.cpp`, and the error messages are identical word for word. XI-18 to XI-20, XE-01 and XE-02 cross-check the two engines. flatfile received one change after this decision was made. `ComputeNewRows` in `src/flat_file_executor.cpp` keeps the stored cell when an assigned value equals it. Because `-0.0` equals `0.0`, `UPDATE zeros SET v = ABS(v)` no longer rewrites a stored `-0.0` as `0.0` when another cell of the row changes. The cross-engine tests found the difference, Design Document 2.4 describes the rule ("Equal value keeps the stored cell"), and XI-25 is the regression test. paged applies the same rule (XU-21).
- **Rejected:** Moving the rules into shared Domain functions (it needs a change to `flat_file_executor.cpp`, and with shared code the equivalence tests could not catch an error in the shared rule itself); `paged/` including the flatfile executor (it breaks the dependency direction, and `TableStore` assumes all rows are in memory).

### ADR-0040: The database-level reader-writer lock lives in `QueryService` and is shared by both engines

- **Decision:** `QueryService` holds one `std::shared_mutex`. `Execute(SelectStatement)` and `DescribeCatalog` take the shared lock. The other statements and `ImportCsv` take the exclusive lock. The lock covers bind and execute. It sits in the Application layer, and both engines share it. See Design Document 2.5.
- **Rationale:** The concurrency contract of the paged storage layer requires the caller to guarantee a single writer (Paged Engine Design Document 2.5), and its scope is many readers and a single writer. The lock sits above the engines, so both engines follow the same rule. flatfile has no in-process lock, and with this lock an entry point added later can handle several requests at the same time and still use both engines directly. The lock covers bind, so no other DDL statement can change the schema that the Binder sees before execution.
- **Cost:** Every reader waits during a write statement, and the I/O inside the statement runs while the lock is held. Concurrent writers are not supported. In return each statement is consistent as a whole, and with a single database-level lock there is no deadlock within a lock hierarchy.
- **Current state:** The lock is implemented in `application.h` and `application.cpp`. `ImportCsv` takes it before the check that a CSV source exists. XU-28 shows that two readers are inside the engine at the same time and that a second `SELECT` and `DescribeCatalog` finish while one `SELECT` is held. XU-29 shows that no call enters while a writer is inside, for each of the five writer kinds. XU-30 shows that bind and execute see the same catalog version while `CREATE TABLE` runs. XI-11 runs 8 readers and one writer (20 updates) through `QueryService` over both engines. The full suite passes under ThreadSanitizer. Fairness and the writer wait time are not measured yet.
- **Rejected:** One lock per table (a cross-table cascade would need several locks and a fixed acquisition order, which the current scope does not need); the lock inside the engines (each of the two engines would implement it, and flatfile has no in-process lock); locking only writes and not reads (a reader would read a page that the writer has half changed); multi-version concurrency control (MVCC, outside the current scope).

### ADR-0041: `.engine` is a session setting, and the data of the two engines in one directory does not interact

- **Decision:** `.engine [flatfile|paged]` sets the engine that `Cli` uses within the session. The setting is `flatfile` at every startup. `.open` opens according to the setting, and when a database is already open, `.engine` reopens the same directory. The flatfile data is `catalog.csv` and the CSV of each table, and the paged data is `paged.db`. The two do not interact, and a directory can hold both at the same time. When the opened result has no table and a file of the other engine (`catalog.csv` or `paged.db`) exists, `Bootstrap` puts one `note:` line into `OpenedDatabase::notes`, and `Cli` prints it. `.engine` is in the command name table of `Cli`, and a hint is given when the `.` is missing. See Design Document 3.4.
- **Rationale:** (1) The engine setting is not data. Writing it into the directory would make the same `.open` depend on which engine was used last time, so the result could not be reproduced. (2) With two sets of data in one directory, the same path can switch engines for comparison. (3) Switching reopens the directory without converting. The data of the two engines is not copied automatically, which avoids a silent data move, because conversion needs schema mapping and conflict handling. The `note:` keeps the user from thinking the data disappeared after switching engines.
- **Cost:** A directory may hold two copies of the data that are out of sync, and every startup returns to flatfile. In return switching engines needs no second path and no data conversion.
- **Current state:** Implemented in `repl.cpp` and `bootstrap.cpp`. The setting is `flatfile` at every start and is not saved (XI-13). `.open` follows the setting, and `.engine <other>` with a database open reopens the normalized directory with the other engine. The setting changes only when that open succeeds (XI-14). A failed reopen prints only `error: could not open <normalized directory>: <reason>`, with no `engine <name>` line, and the database and the setting stay as they were. Only the exact lowercase names are accepted, so `.engine PAGED` gives the usage error. Without the dot, `engine paged` gives `error: commands start with '.'; did you mean .engine`, and `.help` has one `.engine` line (XI-13). `Bootstrap` puts the `note:` line into `OpenedDatabase::notes`, and `Cli` prints it after the `loaded` line (XI-15). The demonstration of Design Document 3.4 runs on the real CLI executable (XI-16).
- **Rejected:** A command-line option `--engine` (the command-line usage stays unchanged, and the option can be added when needed); writing the engine setting into a file inside the directory (the first reason above); converting data automatically when switching (the third reason above).

### ADR-0042: The paged DDL scope is `CREATE TABLE` and import

- **Decision:** `PagedEngine` executes `CreateTableNode` and `ImportTableNode`. `AddColumnNode` and `DropTableNode` return `kUnsupported` with the messages `paged engine does not support ALTER TABLE ADD COLUMN` and `paged engine does not support DROP TABLE`, and both are planned for later. See Design Document 2.8.
- **Rationale:** The cross-engine equivalence tests and `.engine paged` need tables, and creating them through SQL verifies the whole path better than an internal API does. `Catalog::CreateTable` is already completed and tested in the paged storage layer. `.import` loads the same CSV into both engines with the same command, as it was already used to load `data/`, so the timing and Environment tests need no other loading tool. `ADD COLUMN` needs a rewrite of every row and of `sys_columns`, and `DROP TABLE` needs rules for page reclamation, which the paged storage layer leaves out of scope. The design of both is therefore left for later.
- **Cost:** An `.import` that fails midway leaves an empty table, because there is no `DROP TABLE`. The later DDL work also becomes smaller, because the execution of paged `CREATE TABLE` is completed now. What remains for it is the verification of reopening the file, `ALTER` and `DROP`. In return the execution layer can be tested end to end and timed.
- **Current state:** `AddColumnNode` and `DropTableNode` return `kUnsupported` with the two messages and change no page, and so does `CREATE TABLE sys_x` (XI-08, XI-19). `.import` first checks the tuple length of every row, so an overlong row creates no table. It then creates the table and writes the rows through `InsertRows`. An allocation failure midway leaves an empty table and a message that ends with `; table <name> was created` (XI-09). XE-01 imports the three files of `data/` into both engines. The paged file exceeds 540 pages, so pages are evicted in a pool of 64 frames. XE-03 prints the first import timing (ADR-0036).
- **Rejected:** Tests creating tables through an internal API (the path differs from the user's, and the CLI could not switch engines to use them); implementing `ALTER` and `DROP` in the same work (`ADD COLUMN` rewrites every row and `sys_columns`, and `DROP` needs the rules of page reclamation, which are out of scope).

### ADR-0043: paged writes dirty pages after each successful write statement and syncs at `Close`

- **Decision:** `BufferManager::WriteBackAll()` writes out every dirty frame and does not call `Sync`. `BufferManager::FlushAll()` calls `WriteBackAll()` and then `Sync`. `PagedEngine::Execute` calls `WriteBackAll()` after every successful write statement (`INSERT`, `UPDATE`, `DELETE`, `CREATE TABLE`, `.import`) and before it returns. A failed statement and a query do not call it. When `WriteBackAll()` fails, `Execute` returns `kIo` with the message `<message>; statement was applied but not saved`, and the dirty pages stay in the buffer pool. `Database::Close()`, the destructor and `PagedEngine::Flush()` call `FlushAll()`. Before reopening the same directory, `Bootstrap` calls `PagedEngine::Flush()` on the current paged database and aborts the open when it fails. `PagedEngine` holds a `shared_ptr` to the directory lock. Its member order releases the lock only after the `Database` has written out. See Design Document 2.1, 2.8, 3.2 and 3.3.
- **Rationale:** (1) A process terminated by Ctrl-C or `kill` keeps the completed statements in flatfile, because every write statement there reaches the operating system. An interactive user of a SQL terminal expects the same of paged, and writing only at `Close` would lose every statement since the last write out. (2) `FlushAll` plus `Sync` (`F_FULLFSYNC` on macOS) after every statement costs one synchronization to the storage device per statement. The benchmarks would then measure the synchronization cost and not the engine difference. Neither flatfile nor paged calls `fsync` after a write statement, as the current state of ADR-0008 records for flatfile, and `WriteBackAll()` only writes. (3) A write statement runs under the exclusive lock of ADR-0040, so `WriteBackAll()` never runs at the same time as another `FlushAll()` or `WriteBackAll()`, which `BufferManager` requires. (4) Atomicity across several pages and durability on power loss belong to the planned Write-Ahead Log (WAL).
- **Cost:** Every write statement costs one write call per dirty page, and a failure can leave a statement applied in memory but not saved. A statement over several pages that is terminated during its write-back can leave a partial state in the file, because no WAL exists yet (Paged Engine Design Document 2.9). The earlier design carried the same risk only at exit, and it lost every statement since the last write out. In return completed statements survive Ctrl-C and `kill`, as in flatfile. The write-call cost per statement is not measured yet, and XE-03 reports the first timing.
- **Current state:** `WriteBackAll()` writes the dirty frames without `Sync`, and `FlushAll()` calls it and then `Sync` (PU-45). A query, a failed statement and a write statement whose change set is empty do not call `WriteBackAll()`. A change set is empty when no row is selected or every assignment equals the stored value. Such a statement neither saves the dirty pages of an earlier failed statement nor reports `statement was applied but not saved` (XI-24). XI-21 shows that after each write statement a copy of the store holds its effect while `CallCount(kSync)` stays unchanged. XI-22 shows that a failed write-back returns `<message>; statement was applied but not saved`, keeps the dirty pages and lets the next write save them. XI-10 shows that the data survive `Close` and a plain destruction. XI-19 shows that `paged.db` differs from its bytes at open after one write statement, before `Close`. Before reopening the same directory, `Bootstrap` calls `Flush()` without the `QueryService` lock. XI-12 shows that a table that was only in the pool is visible after the reopen. The branch that aborts the open when `Flush` fails has no test. Replacing a paged database through `.open <other directory>` or `.engine flatfile` does not flush first. A failed write-out is printed to standard error by the destructor, and the open is not aborted (Design Document 2.8).
- **Rejected:** Writing out only at `Close` (a process terminated by Ctrl-C or `kill` loses every statement since the last write out); `FlushAll` plus `Sync` after every statement (the second reason above).

### ADR-0044: Equivalence is defined over the result multiset, and the known differences are listed in the Design Document

- **Decision:** Design Document 2.6 defines two engines as equivalent when they agree on the result kind, the columns, the multiset of rows, `AffectedRows`, `tag`, the kind and message of errors, and the content of every table after a series of write statements. With `ORDER BY`, the sequence of sort keys must be identical, and the rows with equal keys form a multiset. The difference table in 2.6 lists the known and accepted differences, and behavior outside the differences must be identical.
- **Rationale:** (1) Without `ORDER BY` the row order is undefined (DesignDocument 2.3). Comparing row by row would make the file order of flatfile an implicit contract that paged has to imitate. (2) A stable sort preserves the input order, and the input order differs by engine, so the order among rows with equal sort keys cannot be compared. (3) The error messages are the contract of DesignDocument 2.5, and comparing them word for word can find a divergence between the rules of two independent implementations (ADR-0039). (4) The difference table states what it means for a test to pass.
- **Cost:** A multiset comparison cannot find out whether the order of rows is reasonable. The difference table is a list that needs maintenance, and when a difference is added, the Design Document and the tests are updated together. In return the tests are not bound to the internal row order of an engine.
- **Current state:** `FindResultDifference` and `EquivalenceRunner` in `tests/test_equivalence_support.cpp` implement the definition of Design Document 2.6. After every statement the runner compares the result kind, the columns, the rows, `AffectedRows`, `tag` and the error kind and message. Rows are compared as the sequence of sort keys with `ORDER BY` and as a multiset without it. After a write statement the runner also compares the catalogs and the content of every table, and checks that a rejected statement changed no table. A statement with `LIMIT` or `OFFSET` and no deterministic cut is reported as outside the comparable set. XI-18 (about 190 statements, LRU and 2Q, 4 frames), XI-20 (3 seeds, 1500 statements each), XE-01 and XE-02 find no difference outside the table. The difference table includes `LIMIT 0`: flatfile reports every error below a `LIMIT 0` and paged drops it, also below a `Sort` or an `Aggregate` (XI-19). The sign of a `DOUBLE` zero is not a difference, because both engines keep the stored cell when an assigned value equals it (ADR-0039). The `ZeroCorpus` statements of XI-18 read the sign back with `CAST(... AS TEXT)`, because the cell comparison cannot see it.
- **Rejected:** Row-by-row, order-by-order comparison (the first two reasons above); comparing only the row count (it cannot catch a wrong value); not comparing error messages (a divergence in the rules of two independent implementations appears only in the messages).
